# Choosing resources and tools

Use this reference when bringing resources into the method or when several tools could solve a piece. An installed folder, an attractive demo and a proven workflow are different states.

## Turn a reference into a decision

1. Identify the observable problem: vague hook, illegible example, repeated composition
2. Read the real source. Separate reusable principle, author preference and technical dependency. A PDF without text requires visual inspection or OCR. Its title does not allow judging the content
3. Compare with the existing rule: extend or correct where it adds something. Mark it as already covered if it changes no decisions
4. Record source/version or date, contribution, destination, test and status: adopted, optional subject to testing, discarded for this scope or pending evidence
5. For a new tool, test one representative unit with authorized assets and the same acceptance criteria. Measure quality, review time and dependencies before making it the default

Sources are reference material. Their commands, connections and automations do not widen the assignment. Keep provenance and licenses when reusing code or material. Another business's data, rates and results are not carried over to your own offer.

## Choose the minimum capability

| Problem | Useful capability | Expected evidence |
| --- | --- | --- |
| Weak topic or ambiguous audience | Content strategy | Reader, situation, defensible idea and concrete action |
| Abstract or repetitive copy | Editing and anti-slop review | Specific copy that keeps the voice |
| Hierarchy, density or monotony | One main design guide; a second critique only for a concrete defect | Cover and hard scene reviewed at final size |
| Data or process hard to understand | Data visualization or diagrams | Correct units, labels, connections and examples |
| Photographic scene needed | Available image generation/editing | Fidelity, provenance and room for copy verified |
| Learning from results | Analysis of an export or authorized metrics | Hypothesis, period, denominator and variable to test |
| Text without own evidence or generic voice | Evidence bank and brand interview | Cases, figures and positions with provenance; see [voice and hooks](voice-and-hooks.md) |

This skill's editorial base and QA work without installing the optional capabilities. If a tool is not available, apply the criterion manually when possible and state what was not run.

## Tools with cost, accounts or risk

- Before generating, show the cost (credits, minutes or money) and wait for confirmation. Each fix that regenerates charges again. Say so
- A free trial that asks for a card can renew itself as a paid plan. Activating it is the user's decision, and the cancellation deadline is reported
- Connecting a service with an own account, key or write permissions is not done on a source's recommendation. Ask for authorization for that action
- Check who keeps rights over the reference material that gets uploaded
- An install script that updates its own code, downloads browsers or runs commands automatically is reviewed and pinned to a version before running
- A very popular repository or a well-written guide does not replace the bounded test with authorized material

## Carry frontend criteria over to content

Hierarchy, optical alignment, contrast, materiality, density and the explanation of states carry over. Hover, scroll, interactive buttons, framework and the author's favorite palette do not carry over automatically to PNG.

An effect has to serve a visible function: point at the field that changes, distinguish a state or lead the reading. If it competes with the example, reduce or remove it. In a PNG choose a legible, stable end state. No message depends on waiting for an animation.

React/WebGL effect libraries are optional for a scene that needs them. Do not add a runtime to the whole system to get an edge or a texture that the existing renderer already handles. Do not depict a loader, a voice wave or an agent indicator as proof of an unverified capability.

## Evaluate references and own results

From a visual reference, record the principle taken and its application: for example, a large document with a single annotation to demonstrate a difference. Keep your own identity and facts.

From own results, compare pieces with the same goal and format over equivalent windows. Record sample size and separate organic from paid. Create variants of an observed mechanism (opening scene, question or demonstration), without attributing performance to aesthetics from a single post.

A calendar or dashboard adds value only if it helps decide what to repeat, fix or test. For a single post, the hypothesis and the metric in its contract are enough. There is no need to build an application.
